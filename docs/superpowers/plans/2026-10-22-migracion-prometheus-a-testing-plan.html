Objetivo

Promover la VM testing (pressticket) a producción. Reemplazar su MySQL, backend/public, .wwebjs_auth y .wwebjs_cache con la instantánea de Prometheus; desplegar el SHA seleccionado de main. Se aprobó transportar el paquete como artifact de Actions cifrado con AES-GCM, usando PRESSTICKET_MIGRATION_KEY y retención de un día.

Fase 1 — viernes 23: runner en testing

  1. Entrar a la consola/RustDesk de la VM; verificar hostname, Ubuntu 24.04, usuario deploy y ruta de repo. No confundir testing con la PC local.
  2. Desde la raíz del repo, confirmar que existe scripts/instalar-runner.sh. Si falta, detenerse y reportarlo.
  3. En GitHub → Settings → Actions → Runners → New self-hosted runner, generar token de registro temporal (el script indica ~1 hora). No compartirlo ni escribirlo en archivo.
  4. Como usuario deploy, instalar con etiqueta pressticket pasando el token en memoria:
read -r -s -p "Token temporal de GitHub: " RUNNER_TOKEN
printf '\n'
bash scripts/instalar-runner.sh "$RUNNER_TOKEN" pressticket
unset RUNNER_TOKEN

El script usa $HOME/actions-runner y PM2 github-runner. En GitHub confirmar runner `Online` y etiqueta `pressticket`; en testing verificar:

pm2 logs github-runner --lines 20

Debe indicar Listening for Jobs. Ejecutar un job inocuo de identidad de host/usuario, sin cambios de aplicación. No usar el deploy de producción para probar.

Fase 2 — configurar deploy de testing en cada push

  1. Confirmar ruta, usuario, DB, servicios PM2, URL y directorios reales de testing.
  2. Preparar un script de deploy específico de testing; no reutilizar el deploy de Prometheus sin adaptar paths/servicios.
  3. Crear workflow que despliegue tras CI exitoso en main, use [self-hosted, pressticket] y aplique el SHA validado. Añadir dispatch manual controlado y exclusión de ejecuciones concurrentes.
  4. Probar con cambio inocuo/dispatch que no borre ni migre datos. Revisar que target, SHA, logs y servicios sean los esperados.
  5. Después de validarlo, pausar el cron por tags con el kill-switch .autodeploy-off existente. Confirmar que no quedan dos deploys activos en testing.

Cutover: al convertir testing en producción, actualizar el workflow productivo para el único destino activo. Evitar que Actions vuelva a arrancar Prometheus con las mismas sesiones o que dos workflows desplieguen concurrentemente el mismo host.

Fase 3 — preflight obligatorio

  • URL pública final y mecanismo de cambio de tráfico confirmados.
  • Ruta de testing, usuario, DB y servicios PM2 confirmados.
  • Espacio real suficiente en origen/destino para backups, paquete cifrado, extracción y reemplazo.
  • Tamaño comprimido del artifact y límite/cuota de Actions comprobados.
  • SHA de main aprobado y sin cambios posteriores durante el corte.
  • Backups de DB, adjuntos, sesiones/cache y código de Prometheus y testing comprobados como recuperables.
  • Secreto GitHub PRESSTICKET_MIGRATION_KEY creado por el usuario y formato de clave de 32 bytes acordado.
  • Herramienta de cifrado/descifrado probada fuera de producción; incluye nonce aleatorio y tag AES-GCM.

Si falla algún punto, no detener servicios ni crear un paquete sin cifrar; postergar y resolver el bloqueo.

Fase 4 — paquete cifrado

  1. Preparar dump MySQL, backend/public, LocalAuth y cache; generar manifiesto con SHA de código, fecha, tamaños y hashes.
  2. Excluir `.env`, credenciales Infisical, llaves SSH, token del runner y secreto de cifrado.
  3. Cifrar con AES-256-GCM y nonce aleatorio único; formalizar representación de la clave de 32 bytes. Subir únicamente el ciphertext como artifact, con retención de 1 día.
  4. Descargar en testing, validar autenticidad GCM y hashes antes de extraer en directorio temporal restringido.

El backup.sh actual no detiene backend, no cifra, no incluye código y presupone `.env`; revisar o implementar un capturador dedicado antes de la ventana.

Fase 5 — ventana de reemplazo

Congelar y capturar

  1. Confirmar ventana con el usuario, SHA y URL de corte.
  2. Pausar despliegues concurrentes; crear y validar respaldo total del destino.
  3. Detener backend en Prometheus y testing. Verificar procesos; no asumir nombres PM2.
  4. Con ambos backends detenidos, capturar dump SQL, public, .wwebjs_auth y .wwebjs_cache de Prometheus.
  5. Cifrar, subir y descargar artifact; comprobar que Actions contiene solo ciphertext.

Reemplazar el destino

  1. Validar GCM y hashes antes de extraer.
  2. Reemplazar DB completamente, eliminando tablas/datos solo de testing. Verificar a mano la DB configurada antes de cualquier operación destructiva.
  3. Reemplazar directorios de media y LocalAuth/cache (no fusionarlos); conservar los backups fuera de las rutas activas.
  4. Actualizar código al SHA acordado de main; conservar secretos y configuración propia de testing. No copiar `.env` desde Prometheus.
  5. Aplicar migraciones del SHA a la DB restaurada y verificar ownership/permisos con el usuario real de servicio.
  6. Arrancar solo el backend de testing con las sesiones migradas.

Validar y promover

  • DB conectada y conteos críticos comparados con el origen.
  • Frontend y API responden en URLs confirmadas.
  • Adjuntos/media de tickets accesibles.
  • WhatsApp conserva sesión o muestra reconexión esperada; Prometheus sigue apagado.
  • Telegram/integraciones esenciales sin errores críticos ni secretos en logs.
  • Procesos PM2 saludables y smoke tests aplicables correctos.
  • Con aceptación explícita, dirigir tráfico a testing y asegurar que deploys futuros van al único destino activo.

Rollback

  1. Detener testing antes de reactivar Prometheus, especialmente tras copiar LocalAuth.
  2. Si corresponde, restaurar backup de testing (DB, archivos y código) antes de devolverlo a su estado previo.
  3. Volver el tráfico al mecanismo/URL confirmado; no improvisar DNS/proxy.
  4. Arrancar únicamente Prometheus con su estado de rollback y registrar posibles escrituras hechas en testing desde el corte.
  5. Desactivar el deploy nuevo hasta resolver la causa. No eliminar backups hasta que el usuario confirme estabilidad.

Gates pendientes

  • Runner online y job inocuo correcto.
  • Resolver rutas discrepantes y confirmar servicios/DB.
  • Confirmar URL productiva y cambio de tráfico.
  • Backup de testing validado; reemplazo destructivo probado de forma segura.
  • Espacio, artifact y cifrado verificados.
  • Definir estado de Prometheus y workflow después del cutover.
  • Confirmar ventana destructiva con el usuario antes de proceder.
