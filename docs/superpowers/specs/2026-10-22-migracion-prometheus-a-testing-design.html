Migración de Press-Ticket de Prometheus a testing

Diseño aprobadoPress-Ticket22/10/2026Ejecutado 24/10/2026

Objetivo: preparar la VM testing (pressticket) para reemplazar Prometheus como producción el lunes 26/10. El alta inicial del runner se prevé desde la consola de testing el viernes 23 después de hora.

Se aprobó reemplazar completamente la base de testing, sus adjuntos y sesiones WhatsApp por los de Prometheus, además de desplegar el commit de main que se seleccione para el corte.

Ejecutado el 24/10/2026: pressticket es producción y prometheus quedó como servidor anterior. Estado vigente en docs/produccion.md.

Plan operativo: abrir el runbook HTML. Fuente: diseño Markdown.

Decisiones confirmadas

  1. Destino: VM pressticket, documentada como Ubuntu 24.04 detrás de CGNAT.
  2. Se permite reemplazar por completo los datos actuales de testing; antes hay que respaldarlos.
  3. Transferir MySQL, backend/public, .wwebjs_auth y .wwebjs_cache.
  4. Se intentará conservar WhatsApp trasladando LocalAuth. Los backends estarán detenidos durante la copia y no se ejecutarán ambas instancias con la misma sesión.
  5. Usar un artifact temporal de Actions cifrado con AES-GCM, secreto PRESSTICKET_MIGRATION_KEY y retención de un día. La clave no va en el chat.
  6. Registrar un runner self-hosted con etiqueta pressticket para despliegue después de CI exitoso.

Estado técnico del repo

  • El workflow actual despliega a Prometheus en [self-hosted, prometheus] y llama scripts/deploy.sh.
  • Ese script apunta a /home/deploy/Press-Ticket y PM2 itn-backend/itn-frontend; no sirve directamente para testing.
  • El auto-deploy actual sigue tags v*; no despliega cada push.
  • Hay rutas discrepantes: docs/tunel-testing.md y scripts/migrate-testing-releases.sh describen /home/deploy/proit-press; scripts/setup-auto-deploy.sh presupone /home/deploy/Press-Ticket. Se debe verificar la ruta real en la consola de testing.
  • scripts/instalar-runner.sh acepta etiqueta por argumento, instala en $HOME/actions-runner y usa PM2 con nombre github-runner por defecto.
  • restore.sh importa sobre la DB existente y extrae archivos encima: no garantiza reemplazo total. backup.sh no detiene servicios ni cifra, depende de `.env` y no incluye código. Ambos requieren revisión/adaptación para este corte.

Tamaños reportados en Prometheus el 22/10: backend/public 602 MB, .wwebjs_auth 4.1 GB, .wwebjs_cache 81 MB; espacio libre 59 GB. El paquete comprimido/cifrado y el espacio libre de testing aún no se midieron.

Transferencia y cifrado

  1. Respaldar por separado el estado de Prometheus y el de testing.
  2. Empaquetar dump SQL, medios, sesiones/cache y metadatos (SHA, fecha, tamaños, hashes). Excluir `.env`, credenciales, tokens y clave AES.
  3. Cifrar con AES-256-GCM, nonce aleatorio nuevo y tag autenticado; definir/formalizar cómo se codifica la clave de 32 bytes.
  4. Subir únicamente el ciphertext como artifact. Verificar tamaño/cuota y espacio antes de detener servicios.
  5. En testing, autenticar el ciphertext antes de extraer. Preparar reemplazo de DB y directorios sin fusionar archivos sobrantes.
  6. Arrancar solo testing con las sesiones migradas; validar aplicación, DB, medios y canales.
Gate de sesiones: después de copiar LocalAuth, no iniciar ni mantener Prometheus y testing usando esas mismas sesiones en paralelo. Ante rollback, detener primero testing.

Deploy por push a main

  • Preparar un deploy específico que use [self-hosted, pressticket], ejecute tras CI exitoso en main y tenga dispatch manual controlado.
  • El script debe apuntar a la ruta real de testing y no reutilizar sin cambios el deploy hardcodeado para Prometheus.
  • Evitar concurrencia entre cron por tags y Actions; pausar el cron solo cuando el workflow nuevo ya haya sido validado.
  • Al pasar a producción, dejar el workflow de producción apuntando al destino activo y evitar que un job vuelva a arrancar Prometheus o duplique el control de WhatsApp.

Datos pendientes de confirmar

  • Ruta, usuario, nombres PM2 y configuración DB reales de testing.
  • URL pública final y mecanismo de cambio del tráfico productivo.
  • Espacio libre real del destino y límite/cuota del artifact.
  • Restauración destructiva exacta y backups utilizables de los dos lados.
  • Rol final de Prometheus y destino del workflow después del corte.
  • Generación/carga en GitHub del secreto y formato acordado de la clave.

Aceptación

  1. Runner online en la VM correcta; job inocuo confirma host/usuario.
  2. Push de prueba validado por CI despliega el SHA exacto en testing.
  3. Artifact únicamente cifrado; autenticidad comprobada antes de extracción.
  4. DB y archivos de destino reemplazados por completo y contrastados con origen.
  5. WhatsApp validado con Prometheus detenido y rollback documentado.
  6. URL productiva sirve testing y los deploys posteriores apuntan a un solo destino activo.
